# Request diagnostics and authentication query reduction

Each HTTP response receives a generated X-Request-ID. Support can correlate this reference with structured request logs. Caller-supplied IDs are never trusted or reflected. Logs contain the generated reference, allowlisted HTTP method, route template, status, duration, successful SQL statement count, SQL duration and new database connection duration. They omit request bodies, cookies, headers, source, user identifiers, raw URLs, query strings and exception messages. Unknown or early-rejected routes log as unmatched.

The supervised API disables Uvicorn's default raw access logs. Structured request records use the configured Uvicorn error logger at INFO; static workers emit JSON scan-finished records with job ID, status, attempts, queue wait and elapsed duration. A stale publication logs discarded rather than completed. SQLAlchemy hides bound parameters in error representations. Platform logging and exception tracebacks are separate from these diagnostic records; production log access and retention still need operational policy.

Server-Timing reports app time up to response headers, successful SQL execution time and new database connection establishment time. Reused connections report zero new connection time. SQL timing excludes pool acquisition, connection establishment, commit, network transit and browser rendering. Structured request duration includes response delivery inside the server. Neither metric is an end-to-end browser latency or a reliable cold-start measurement. Failed SQL statements are not included in the successful-statement count.

Authentication now joins session and verified user in one database query and reuses that identity snapshot only within the same HTTP request. Staging authentication and endpoint authentication no longer repeat the same lookups. CSRF is always checked for mutations; membership and roles are checked separately. Every new request rechecks the database, including after logout, password change, session expiry or member demotion. No cross-request authorization cache is introduced.

A controlled local profile executes staging authentication plus organization membership10 times with each implementation against the same disposable SQLite database. The trusted baseline is commit9e78cde. SQL statements fell from5 to2 for every sample; median component time was0.932ms before and0.564ms after in this run. This is a narrow local measurement, not a PostgreSQL/network throughput claim. Run `python -m scripts.profile_auth_queries` after local QA seeding to reproduce. The first hosted baseline attempt timed out during login. One retry completed: login8.057s, warm report median0.280s, warm review-save median0.325s (three sequential pairs). These measurements differ materially from the historical7.95s save, so that historical single request is not a steady-state baseline. A hosted before/after comparison must use the same synthetic reports and client conditions; failed attempts are documented as blocked rather than substituted with historical timings.

Unhandled errors return a generic message and request reference, no exception contents. Request references and timing diagnostics are available on normal validation/authentication errors too. There is no external telemetry provider, alert delivery or security certification. No new infrastructure or migration is required.
